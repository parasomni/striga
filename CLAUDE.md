# Striga Attack Framework

Python CLI that automates authorized penetration-testing workflows: port scanning → service enumeration → vulnerability evaluation → exploitation via Metasploit. Wraps external tools (nmap, rustscan, nuclei, nikto, enum4linux, smbclient, smbmap, ffuf, gobuster, dirbuster, feroxbuster, sslscan, wpscan, sqlmap, ldapsearch, dnsenum, nslookup, snmpbulkwalk, whatweb, whois, httpx, msfconsole) behind a common pipeline and a YAML config. An optional local-LLM findings-evaluation layer (`evaluation/ai`, Ollama by default) triages saved tool output.

Intended for use only against systems the operator is authorized to test (labs, CTFs, engagements with signed scope). Do not add features that broaden targeting beyond what a user explicitly requests, and do not weaken the existing input validation.

## Entry point & flow

- `striga.py` is the main entry point (installed as `striga` via `install.sh`, deployed to `/opt/striga`).
- `install.sh` auto-detects the distro (`/etc/os-release` `ID`/`ID_LIKE`, Arch vs Debian-family) and installs/configures Docker before installing striga itself, since the GitHub PoC sandbox is otherwise nearly impossible to get working from a cold host: installs `docker`/`docker.io` via the right package manager, enables the service, merges (never overwrites) a real `dns` entry into `/etc/docker/daemon.json` (systemd-resolved's stub-resolver-in-a-container gotcha), fixes `SystemdCgroup = false` in `/etc/containerd/config.toml` if a standalone containerd is present (Arch-typical; Debian's `docker.io` bundles its own private containerd and doesn't have this file), and switches `docker-default`/`podman`/`crun`/`runc`/`buildah` AppArmor profiles to complain mode if `aa-status` shows them enforcing (observed blocking legitimate container operations with unhelpful "permission denied" errors on Arch — everything else AppArmor confines is left alone). Ends with a `docker run --rm hello-world` smoke test; on failure it prints known-cause guidance rather than trying to auto-fix everything — deliberately does **not** attempt to auto-downgrade `runc`/`libpathrs` for the version-regression case encountered during development, since that requires a specific package version pin from the Arch Linux Archive that will go stale and may not even apply to whoever's installing later. If you add another host-level Docker fix discovered through troubleshooting, add it to this section following the same pattern (detect the actual condition, fix only that, don't blanket-disable a whole security layer) rather than only documenting it here.
- Pipeline stages, each its own package:
  - `scanner/` — port/vuln scanning (nmap, nmap-vuln, rustscan, nuclei, nikto). `scanner/scanner.py` dispatches by config. `scanner/nmap_scanner.py` does a **two-phase scan** by default (see "Performance architecture"); `scanner/port_utils.py` parses open ports **and** vhost hostnames out of the nmap text.
  - `enumeration/` — per-service enumeration modules under `enumeration/<service>/` (web, smb, dns, sql, ldap, snmp). `enumeration/enumerator.py` orchestrates; results are keyed off services nmap detects. Web modules: ffuf, gobuster, dirbuster, feroxbuster, whatweb, webtech, whois, nmap-http, sslscan, wpscan, vhostfuzz. SMB: enum4linux, smbclient, smbmap. SNMP: snmpbulkwalk (dispatched when nmap tags `snmp`).
  - `evaluation/` — `evaluation/presenter.py` renders stored results per service/scan-id; `evaluation/services.json` lists presentable services.
  - `exploitation/` — `exploitation/exploit_launcher.py` maps CVEs (via `cve_mappings.json`, MITRE/Vulners APIs) to Metasploit modules and drives `msfconsole` through `pymetasploit3`. It falls back to the GitHub PoC pipeline (see below) both when no Metasploit module ranks `excellent`/`great` for a CVE **and** when a module was found but ran without obtaining a session — `run_exploit()`/`run_msf_exploit_console()` return a real `True`/`False` session-obtained signal for this; `cve_mappings.json` only ever caches a CVE->module mapping on confirmed success, so a module that exists but doesn't work against this target isn't retried from cache forever while silently starving the GitHub fallback.
  - `core/` — shared plumbing: `config_manager.py` (singleton YAML config), `arg_parser.py`, `logger.py`, `scan_id.py`, `check_dir.py`, `module_adder.py`/`scanner_adder.py` (pluggable module registration), `concurrency.py` (`bounded_gather` — global concurrency cap), `vhost.py` (hostname/virtual-host selection + non-persistent routing).
- Enumeration and scanning run asynchronously (`asyncio`) per target; results are written under `/etc/striga/<scan_id>/<target>/`.
- `core/logger.py`'s `Logger` writes `framework.log` per scan ID (`<scan_id>/logs/framework.log`), not one shared file — the path is computed fresh on every `log()`/`debug()` call from the *current* `config.scan_id` (via `_log_file()`), not cached once at `Logger.__init__()`, since `scan_id` isn't known yet at that point (it's set later in `run_striga()`, and can change again on `--continue`/`--continue-scanid`). Pre-scan-id startup chatter (before `args` are even parsed) lands under `scan-default` (`ConfigManager`'s initial placeholder value) — expected, not a bug. Don't cache the log file path on the `Logger` instance again; that's exactly what caused every scan to share one global log file before this was fixed.
- `utils/` holds standalone scripts (e.g. `revshells.py`, `pwdfinder`) invokable as `striga <script>`; `run_script()` in `striga.py` validates script names against `^[a-zA-Z0-9_]+$` before dispatch — preserve that validation in any change to script execution.
- `reverse_shells/` and `utils/reverse_shells/` contain reverse-shell payload templates used by `revshells.py`.

## Web tech fingerprinting → CVE lookup → GitHub PoC exploitation

Extends the exploit pipeline beyond Metasploit:

1. `enumeration/web/webtech_enum.py` runs `whatweb --log-json=- -a 3` (whatweb is already a Wappalyzer-class fingerprinter — this doesn't reimplement one) against each discovered web port (see "Per-port web enumeration" below) and normalizes plugin/HTTP-server hits into `{product: version}`.
   - `_extract_products()` handles two shapes in whatweb's JSON: plugins with an explicit `"version"` array, and presence-only plugins (`X-Powered-By`, `HTTPServer`, most CMS/framework detections) that only carry a `"string"` value like `"Next.js"` or `"Apache/2.4.41"` (split on `/` into name+version if present, else recorded with an empty version). Originally the `"string"` fallback only applied to the one special-cased `HTTPServer` plugin — every other presence-only detection (e.g. `X-Powered-By: Next.js`, visible fine in whatweb's own human-readable output) was silently dropped from the JSON path entirely. If you add a new whatweb-derived signal, make sure it goes through this same fallback rather than requiring an explicit `"version"` field, or it'll disappear the same way. `skip` excludes plugins that are response *metadata* rather than a product name (`UncommonHeaders`, `Meta-Author`, `Email`, ...) — since the fallback is now generic, a plugin whose `"string"` value is a header list or email address would otherwise get fed to the CVE lookup as if it were a technology name; add any newly-noticed metadata-only plugin here rather than to the CVE lookup's exclusion logic.
   - `_run_wappalyzer_supplement()` then runs the real Wappalyzer fingerprint DB (`python-Wappalyzer`, `requirements.txt`) as a second, best-effort pass over the same URL and fills in anything whatweb still missed (only fills gaps — `if version and not products.get(name)` — an empty-string version from the fallback above still counts as "needs filling", never overwrites a version whatweb already found). Synchronous/blocking (the package uses `requests` internally), run via `asyncio.to_thread()` so it doesn't stall other concurrent enum tasks; any failure (package missing, network hiccup, parse error) is caught and logged at `debug` only — webtech detection must keep working with whatweb alone if `python-Wappalyzer` isn't installed or fails. The `except ImportError as e:` around the `from Wappalyzer import ...` logs the real exception message, not a blanket "not installed" — that distinction matters because `python-Wappalyzer` (unmaintained since 2020) can be *installed* and still fail to import.
   - `requirements.txt` pins `setuptools<81`: `python-Wappalyzer` internally does `import pkg_resources` (legacy setuptools API), which very recent `setuptools` releases have started dropping entirely as part of the broader `pkg_resources` deprecation — installing `python-Wappalyzer` alone is not sufficient on a modern Python, the venv also needs an older `setuptools` that still bundles it. If bumping the `setuptools<81` ceiling ever becomes necessary for an unrelated reason, re-verify `import Wappalyzer` still works before doing so.
   - `_run_httpx_tech_supplement()` is a **third** fingerprinting pass, added because `python-Wappalyzer`'s bundled fingerprint DB is frozen circa 2020 and can itself miss things (observed missing a Node.js version whatweb also missed). It shells out to `httpx` (ProjectDiscovery's Go CLI — **not** the unrelated Python `httpx` HTTP client library of the same name) with `-tech-detect -json -silent`, which uses `wappalyzergo`, an actively-maintained Go port of the fingerprint format that ProjectDiscovery keeps current. Parses httpx's `"tech": ["Next.js:15.0.1", "React"]` field (colon-separates name/version, bare name when no version known) and merges into the same gap-filling policy as the Wappalyzer supplement (`if version and not products.get(name)`). Same best-effort contract: `httpx` not installed (`FileNotFoundError`), timeout, or unparseable output all degrade to `{}` at `debug` level rather than breaking webtech detection. `httpx` is an external Go binary like `nmap`/`whatweb`/`nuclei` — not something `requirements.txt`/`install.sh` installs; assumed pre-installed the same way those are.
     - **Real binary-name collision, not just a theoretical one**: `pip install httpx[cli]` (a dependency of something else, or installed directly) puts a console-script also named `httpx` on `PATH`, and if it resolves before ProjectDiscovery's Go binary (e.g. because it's in the venv's `bin/`, prepended to `PATH` while the venv is active), the wrong tool runs silently. `WRONG_HTTPX_MARKERS` recognizes this specific collision by checking the failed process's stderr for flags unique to the Python CLI's `--help` output (`--follow-redirects`, `--http2`, `--params` — none of which appear in ProjectDiscovery's httpx), and surfaces one clear, actionable `logger.log()` (not debug) the first time it's hit per process (`_warned_wrong_httpx` module-level flag — de-duplicated so it doesn't repeat once per port per target). `web_tech_lookup.httpx_binary` (`config.yaml`, defaults to bare `httpx`) lets the operator point at the correct binary's full path (e.g. `~/go/bin/httpx`) to resolve it permanently instead of fighting `PATH` order. If you add another external tool with a name collision risk like this, follow the same pattern: a config override for the binary path, plus output-based detection of "wrong tool ran" rather than a generic failure message.
   - Merged result written to `<scan_id>/<target>/webtech_<port>.json` — one file per web port.
2. `exploitation/cve_finder.py` (`lookup_cves_for_target`) reads *every* `webtech_<port>.json` for the target (globbed, not a single fixed filename) and queries Vulners' software-search endpoint plus the NVD CVE API 2.0 for each `{product, version}` pair. `striga.py`'s `exploiting()` merges the resulting CVE list into the vuln results dict as `webtech-cve` before handing off to `exploit_from_cve_results`, so it flows through the normal CVE→exploit path.
3. `exploitation/exploit_launcher.py`'s `search_for_exploits` calls `github_exploit_fallback(cve, target)` whenever Metasploit has no ranked module for a CVE:
   - `exploitation/poc_search.py` looks up the CVE in the curated `nomi-sec/PoC-in-GitHub` index (not live GitHub search — much higher precision, no token needed).
   - `exploitation/poc_vetting.py` downloads the candidate as a zip (`codeload.github.com`, no `git clone` — nothing executes on fetch) and statically scans it for red flags (obfuscation, `curl|sh` patterns, destructive commands, exfil/miner indicators) before anything runs.
   - `exploitation/sandbox_runner.py` executes the vetted PoC in a disposable, non-root, read-only, resource-limited Docker container on a dedicated bridge network. When running as root, `DOCKER-USER` iptables rules pin that network's egress to the target IP and `LHOST:LPORT` only, so a trojanized PoC can't exfiltrate or call home elsewhere; `sandbox.strict_egress` (default `true`) refuses to run unsandboxed-network PoCs if not root.
     - `NetworkIsolation._wait_for_docker_user_chain()` polls (up to 8x, 0.75s apart) for the `DOCKER-USER` chain before inserting rules — `docker network create` returns as soon as the API responds, but dockerd's own netfilter setup can still be finishing asynchronously right after.
     - Every `iptables` invocation goes through `_iptables_cmd()`, which adds `-w 10` (wait up to 10s for `/run/xtables.lock` instead of failing immediately on contention) — good practice regardless, though on the host where this was debugged it turned out not to be the actual cause (ruled out: still failed 8/8 with `-w` in place).
     - `NetworkIsolation._ensure_docker_user_chain()` is a **self-heal fallback**: if the chain still isn't there after waiting, create it (`-N`, harmlessly no-ops if it already exists) and hook it into `FORWARD` ourselves (`-I FORWARD 1 -j DOCKER-USER`, checked via `-C` first to avoid a duplicate hook) — the same bootstrapping dockerd itself does at daemon startup. This exists because on at least one real host, dockerd was not reliably keeping `DOCKER-USER` present across repeated `docker network create`/`network rm` cycles (each failed sandbox attempt tears its own temp network down in cleanup) — waiting longer and adding `-w` did not fix it, only creating the chain directly did. Don't remove this fallback on the assumption dockerd always manages this chain correctly; empirically, on some hosts it doesn't.
     - `exploitation/sandbox_images/<name>.Dockerfile` + `_ensure_image_built()`: the `.py` sandbox image is `striga-sandbox-python:3.12` (see `CUSTOM_IMAGE_DOCKERFILES`), built locally on first use from `sandbox_images/python-poc.Dockerfile` rather than pulled from a registry (it's a local-only tag; a plain `docker run` would otherwise fail trying to pull it). It pre-installs common PoC dependencies (`requests`, `paramiko`, `pwntools`, `beautifulsoup4`, `dnspython`, `pycryptodome`, plus `build-essential` since some of those need to compile native extensions) because the sandbox's egress is locked to target+`LHOST:LPORT` only — a PoC can't `pip install` a missing import at runtime (PyPI isn't in the allowlist), so anything it needs has to already be in the image. If a PoC still fails on a missing import, add the package to that Dockerfile rather than trying to special-case runtime installation (which would require punching a PyPI-shaped hole in the egress restriction, undermining the whole point of it). The build itself runs with `docker build --network=host` — build steps (apt/pip) use the host's network namespace directly instead of the default `docker0` bridge, deliberately sidestepping host-specific bridge/NAT/DNS issues that are unrelated to the sandbox's actual (separately-managed, per-run) restricted network. This is safe: it's a one-time image build, not the PoC's sandboxed runtime network.
   - Image builds use `_run_streaming()` (plain `subprocess.run(cmd)`, output inherited straight to the terminal), not `_run()` (which uses `capture_output=True` and buffers everything until the process exits) — a multi-minute `pip install` under `capture_output` looks completely frozen with zero feedback until it finishes or gets killed. Keep builds on the streaming path; only use buffered `_run()` for fast operations (iptables, docker network create/rm, image inspect) where capturing output to log on failure matters more than live feedback.
   - `ensure_default_sandbox_images()` builds every `CUSTOM_IMAGE_DOCKERFILES` entry **once, up front**, called from `init_launcher()` (gated on `github_exploit_search` actually being enabled, i.e. respects `--skip-github-poc`) — not lazily inside `run_poc_in_sandbox()` the first time some PoC candidate happens to need it. Building lazily mid-loop meant the (multi-minute, for `pwntools`) first build silently stalled the exploitation run in the middle of a PoC confirmation prompt, with no indication anything was even happening. `_ensure_image_built()` itself still no-ops immediately if the image already exists, so this proactive call is cheap on every run after the first. **Editing `python-poc.Dockerfile` alone does not trigger a rebuild** — `_ensure_image_built()` only builds when the tag is entirely absent, so after adding a package, `docker rmi striga-sandbox-python:3.12` first to force the next run to pick up the change.
   - `run_poc_in_sandbox()` no longer blindly invokes every PoC as `<script> <target> <lhost> <lport>` (fixed positional args) — real-world PoCs overwhelmingly use `argparse` with named flags instead (`-t/--target`, `--rhost`, `-H`, `--lhost`/`--lport`, etc.), and the fixed-positional guess failed against nearly every PoC tried in practice. `_detect_invocation_args()` runs the PoC with `--help` first (isolated: `--network none`, 15s timeout, via `_run(..., timeout=...)`), parses `-x PLACEHOLDER`/`--xx PLACEHOLDER` pairs out of the output with `FLAG_PLACEHOLDER_PATTERN`, and categorizes each via `_categorize_flag()` — critically keying off the **placeholder** (`TARGET`, `HOST`, `LHOST`, `LPORT`, ...) as well as the flag name, since short flags like `-t`/`-H` carry no signal alone. `lhost`/`lport` are checked *before* the generic target keywords so `--lhost` (which contains the substring `host`) doesn't get miscategorized as the target flag. Falls back to the original positional convention only if `--help` yields no recognizable flags at all (plain `sys.argv`-reading scripts that don't understand `--help`). This is a regex heuristic, not a general solution — it won't fill in PoC-specific required args it can't map to target/lhost/lport (e.g. a `--webhook`/SSRF-callback flag), and can occasionally guess a flag whose real semantics differ from what the name suggests. The always-visible failure output (invocation + PoC stderr) is the fallback for cases this heuristic gets wrong; don't try to make this "smarter" via an LLM call without also handling the prompt-injection risk of feeding it attacker-controlled `--help` text from an unvetted PoC.
   - The PoC's container now runs with `-w /poc` (also applied to the `--help` probe) — PoCs that reference sibling files via relative paths (`open("ssl-ports.txt")` etc., common in scripts shipped with a data file alongside the exploit script) previously failed with `FileNotFoundError` because the container's default working directory wasn't the mounted PoC directory.
4. **Human-in-the-loop by default**: before executing a fetched PoC, the operator is shown its static risk flags and prompted to confirm. `--no-confirm` (`config.no_confirm`) skips the prompt for full `--auto-exploit`/`--auto-all` automation, but PoCs the static vetting scored `high` risk are still skipped even under `--no-confirm` — that carve-out is intentional and shouldn't be silently removed; if it's ever loosened, do it explicitly and call it out.
   - `search_for_exploits()` threads an `attempts` list (built via `_record_attempt()`) through `_try_msf_module_or_github()` and every call to `github_exploit_fallback()`, recording every Metasploit module and GitHub PoC that was tried, skipped (declined by operator, high-risk under `--no-confirm`, unsupported language, no runnable entry), or run (success/failed). `exploit_from_cve_results()` prints this and writes it to `<scan_id>/<target>/exploitation_summary.txt` via `_print_and_save_exploitation_summary()`, so anything that didn't succeed automatically can be reviewed and re-tried manually. Registered in `evaluation/services.json` under `"exploitation"` so `--show-service exploitation` displays it too. Any new exploit-attempt code path (e.g. a future third fallback source) should call `_record_attempt()` the same way rather than being silently left out of the summary.
5. Public PoCs for popular CVEs are a known malware vector (trojanized "exploits" that backdoor the *operator*, not the target). The vetting + sandbox + egress-restriction layers reduce that risk, they don't eliminate it — don't present auto-execution of arbitrary GitHub code as safe, and don't remove the confirmation gate or the egress restriction as a "convenience" fix.
6. New external dependency: `docker` (already present on the reference host). New config sections: `web_tech_lookup`, `github_exploit_search`, `sandbox` in `config.yaml`.
7. `--auto-all` runs `enumeration(target)` and `exploiting(target)` **sequentially per target** via `full_pipeline()` in `striga.py` (gathered *across* targets, so cross-target concurrency is preserved) — this is intentional and fixes a real race: `exploiting()`'s CVE lookup reads `webtech.json`, which only exists once `enumeration()`'s `webtech_enum` task has completed. Don't go back to `asyncio.gather(*[enumeration(t) for t in targets], *[exploiting(t) for t in targets])`; that reintroduces the race for `--auto-all` specifically (`--auto-enum`+`--auto-exploit` run as separate sequential loops already, so they're unaffected).
8. `exploitation/sandbox_runner.py`'s `docker_daemon_available()` checks `docker info` **once per process** and caches the result — a broken Docker setup (permission denied, daemon not running) is checked once in `github_exploit_fallback` before the candidate loop, not re-discovered per PoC candidate per CVE (which used to burn a full download+static-vet cycle per candidate only to fail identically at the sandbox step every time). Keep this cache in place; don't move the docker check back inside the per-candidate loop.
9. `exploitation/poc_vetting.py`'s `fetch_poc()` resolves the repo's actual default branch via the GitHub API (`api.github.com/repos/<repo>`) before falling back to guessing `main`/`master` — guessing alone silently failed to download candidates using any other default branch name.
10. `exploitation/exploit_launcher.py`'s `find_entry_file()` also reports unsupported-language extensions it saw (`.c`, `.cpp`, `.go`, `.rs`, `.java` — `UNSUPPORTED_LANGUAGE_HINTS`) when it can't find a runnable entry point, since PoCs for memory-safety/race-condition CVEs (e.g. regreSSHion/CVE-2024-6387) are frequently C source requiring compilation, which the sandbox doesn't support. This is diagnostic only — the sandbox still only runs `SUPPORTED_ENTRY_EXTENSIONS` (`.py/.sh/.pl/.rb/.php`); adding a compile-then-run path for C/Go/Rust would be a separate, larger change (needs a build image + a distinct "compile" step before the resource-limited run, and the static vetting patterns would need review for compiled-source-specific risks).
11. `exploitation/poc_search.py` filters candidates by repo name + description before they're even fetched (`_looks_like_discovery_script`, config `github_exploit_search.exclude_discovery_scripts`, default `true`): the PoC-in-GitHub index mixes real exploits in with detection/patch/mitigation tooling for the same CVE (e.g. `CVE-2024-6387_Check` only checks whether a host is vulnerable, it never produces a shell), which used to waste a full download+vet+sandbox-confirmation cycle per false-positive candidate. An explicit exploit/PoC keyword always overrides a discovery-ish one in the same text. This is a name/description heuristic, not code analysis — don't oversell it as more than "filters the obvious cases."
12. `--continue`: `enumeration()` in `striga.py` now skips scanning **and** the entire enumeration task set (not just the nmap port scan) whenever a cached `nmap.txt` exists for the target under that scan ID — it returns immediately rather than re-running ffuf/gobuster/whatweb/webtech/etc. against already-known ports every time. `exploiting()` mirrors this: it loads the cached `vuln_results.json` as a dict (rather than leaving `vulnerabilities` as `""`, which used to silently skip the webtech-CVE merge too) when continuing with a cache present, and only falls back to a fresh `run_scanners()` call if no cache exists yet. The webtech-derived CVE lookup (`lookup_cves_for_target`, reads cached `webtech_*.json` off disk) now always runs regardless of continue/cache state, since it's a cheap local read, not a rescan. If you touch this logic again, preserve the "skip only if genuinely cached, otherwise do the real work" fallback — `--continue` must never silently produce empty results just because a cache file happens to be missing.

## Per-port web enumeration

All web-facing enum modules (`ffuf`, `gobuster`, `dirbuster`, `feroxbuster`, `whatweb`, `webtech`, `nmap-http`, `sslscan`, `wpscan`, `vhostfuzz`) take `(target, port=80, scheme="http", host=None)` — the `host` kwarg is the discovered virtual host (see "Virtual host / hostname handling"). Discovery flow:
- `scanner/port_utils.py`'s `extract_web_ports()` regex-parses the nmap scanner's default `-sV` text output (the same `scan_results` string already captured in `enumeration()`/`striga.py`) for every open TCP port whose service name contains `http` (covers `http`, `https`, `http-proxy`, `http-alt`, `ssl/http`, etc.), returning `{port, scheme, service}` per match. `scheme` is `https` when the service string mentions `ssl`/`https`, else `http`.
- `enumeration()` (`striga.py`) and `run_enumerator()` (`enumeration/enumerator.py`) both fan a web-enum task set out **per discovered port**, not once. `run_enumerator()` can be invoked standalone (`--enum web`) without a fresh scan in that call, so its `_discover_web_ports()` reads the target's last `nmap.txt` off disk instead; if neither a live scan nor a cached `nmap.txt` exist, both fall back to a single port-80/http guess (preserves old behavior rather than skipping web enum entirely).
- Result files from these modules are now `<tool>_<port>.txt`/`.json` (e.g. `ffuf_8080.txt`, `webtech_8443.json`), not a single `<tool>.txt` — necessary since one target can have multiple web ports each producing distinct results. `evaluation/presenter.py`'s `show_service()` was updated to glob `<tool>*.txt`/`<tool>*.json` per tool instead of an exact filename match; keep that glob (not an exact match) if you add another per-port tool.
- `--show-module <name>` (`presenter.show_module()`) shows a single module/tool's saved results directly (across every target in the scan, same per-port glob as `show_service()`), without needing to know or specify which service category it belongs to — validated against `get_module_names()` (the flat union of every service's tool list in `services.json`), so a typo is rejected the same way an unknown `--show-service` is. Complements rather than replaces `--show-service`: use `--show-module` when you want one specific tool's output without the noise of every other tool in that service.
- If you add a new web-enum module, give it the same `(target, port, scheme, host=None)` signature and per-port result filename — don't reintroduce a bare-target/port-80 assumption — and route the vhost via a Host header / SNI as the existing modules do (see below).
- **`whatweb_enum` is intentionally NOT in the automatic fan-out anymore.** `webtech_enum` already runs `whatweb --log-json -a 3` internally (plus the Wappalyzer/httpx supplements), so dispatching `run_whatweb_enum` too would launch whatweb twice per port. Fingerprinting goes through `webtech` only; the `whatweb_enum` module still exists but isn't wired into `enumeration()`/`run_enumerator()`. Don't re-add it to those loops.

## Module enable/disable overrides

`--enable-module <name>` / `--disable-module <name>` (repeatable, applied in `run_striga()` in `striga.py`, after `--config` is loaded so overrides always win) flip a module's `enabled` flag in the in-memory config for that run only — `config.yaml` on disk is never touched. Resolution lives in `ConfigManager.set_module_enabled()` (`core/config_manager.py`):
- Scanner-group tools (`nmap`, `whatweb`, `sqlmap`, etc.) are matched against `config["scanner"][<name>]["enabled"]` — this also transparently affects `get_tool_flags()`, since it mutates the same dict in place.
- Standalone feature groups (`web_tech_lookup`, `github_exploit_search`, `sandbox`) are matched by group name directly, with short aliases (`webtech`, `github_exploit`) defined in `ConfigManager.MODULE_GROUP_ALIASES` so the flag can use the same short names shown by `--list-modules`/`--list-scanners`.
- Unknown module names are rejected (logged, not silently ignored) rather than added as new config keys — keep it that way; silently creating config entries from a CLI typo would be a worse failure mode than an explicit error.

`ConfigManager.set_config_value(attribute, group, value)` is the generic counterpart to `get_config_value()` for this same "CLI flag overrides config.yaml for this run only" pattern, used for single values rather than module `enabled` flags — e.g. `--exploit-timeout SECONDS` overrides `sandbox.timeout` (read live by `sandbox_runner.py`'s `_cfg()`/`run_poc_in_sandbox()` on every call, so the override just works with no further wiring). Prefer this over ad-hoc `config.config[...] = ...` mutation for any future single-value CLI override.

## Performance architecture

Config lives under a `performance:` section in `config.yaml`. All of this is about cutting scan/enum wall-clock without losing findings.

- **Two-phase nmap scan** (`scanner/nmap_scanner.py`, `performance.two_phase_scan`, default `true`): phase 1 is a fast full-range **discovery** sweep (`-p- -T4 -Pn -n --min-rate=<performance.discovery_min_rate> -oG -`, **no `-sV`**), phase 2 runs `-sV` + NSE scoped to `-p <open-ports>` only. This avoids paying version-detection cost across all 65535 ports (the old single-command `-sV -p-` was the dominant time sink). `run_nmap()` still returns/writes the same `-sV` **text** the rest of the pipeline parses, and keeps the old contract (`{}` on hard failure, `""` when nothing is open). Falls back to single-phase on discovery failure or when the toggle is off (then it uses `scanner.nmap.flags` verbatim). Phase 2 also injects `--script ssl-cert,http-title` (`performance.hostname_scripts`, default on) so certs/redirects surface for vhost extraction — cheap because it's port-scoped.
- **Port-scoped `nmap-vuln`** (`scanner/nmap_vuln_scanner._scoped_port_flags`): reads the target's cached `nmap.txt`, and if the operator hasn't pinned ports itself, prepends `-p <open-ports>` so the vuln scan only touches known-open ports instead of re-scanning the default top-1000. No cache yet (e.g. `--auto-exploit` with no prior enum) → unchanged behaviour.
- **Global concurrency cap** (`core/concurrency.py`): `bounded_gather(coros)` is a drop-in for `asyncio.gather` that runs at most `performance.max_concurrency` (default 24) coroutines at once, via **one process-wide semaphore** (lazy-created on the running loop). Applied to every **leaf** subprocess fan-out: enumeration task sets + fingerprint passes in `striga.py`/`enumerator.py`, and `run_all_scanners` in `scanner/scanner.py`. **NOT** applied to the `--auto-all` cross-target gather — those are orchestrator coroutines (`full_pipeline`) that internally await the same semaphore their children need; bounding them would deadlock. Keep the cap on leaves only.
- **Parallel CVE lookups** (`exploitation/cve_finder.lookup_cves_for_tech`): per-product Vulners+NVD lookups run in a bounded `ThreadPoolExecutor` (was a serial blocking loop). Optional NVD API key via `web_tech_lookup.nvd_api_key_file` (untracked) raises the rate limit; one 6s retry on 429/403.
- **Misc fixes made alongside:** `ConfigManager.clean_cache()` uses `shutil` (not `os.system("rm -rf …/*")`); the DNS enum tasks were being appended **uncalled** (`append(fn)` not `append(fn(target))`) so DNS enum never ran — fixed in both call sites; `rustscan_scanner.py` had two bugs (flags list wrapped into one argv element; `output.split("")`) — fixed. `nmap` default flags gained `-Pn -T4`; `nuclei` gained `-severity low,medium,high,critical -rate-limit 150 -timeout 8`.

## Virtual host / hostname handling

Web enum used to always hit the bare CLI `target` (usually an IP), so name-based virtual hosts served the wrong site and SNI-TLS mismatched. Now:

- `scanner/port_utils.extract_hostnames(nmap_output)` regexes vhost/DNS names out of the nmap text (rDNS scan-report line, TLS cert `commonName=`/`DNS:` SANs, HTTP redirect `Location`), normalizes (wildcards → base domain, lowercased, IPs/`localhost` dropped), order-preserved. `is_ip_literal()` and `extract_open_port_numbers()` live here too.
- `core/vhost.py`: `select_vhost(target, hostnames)` picks the vhost — respects an operator-supplied hostname target (returns `None` = use target as-is), else the first discovered name; gated by `web_enum.use_vhost` (default on). `enumeration()`/`run_enumerator()` compute the vhost once and thread `host=vhost` into every web module.
- **Routing is deliberately NON-persistent** (do not change this to editing `/etc/hosts` — that was explicitly rejected as unwanted system persistence): tools connect to the reachable **IP** and route the vhost at the protocol layer. `curl_style_vhost_flags()` adds `-H "Host: <vhost>"` (+ `-k` on https, de-duplicated) for ffuf/gobuster/feroxbuster; sslscan gets `--sni <vhost>`; nmap-http gets `--script-args http.host=<vhost>`; dirbuster/wpscan put the vhost in the URL (no Host override available). For names that don't resolve, `suggest_unresolved_hosts()` only **logs the `/etc/hosts` line** for the operator to add — it never writes it.
- **`vhostfuzz`** (`enumeration/web/vhostfuzz_enum.py`) runs the **ffuf binary** under its own `vhostfuzz` config key (like nmap-http reuses the nmap binary) to fuzz `Host: FUZZ.<domain>` with `-ac` auto-calibration. `registrable_domain()` (last two labels) derives the fuzz base from the vhost/target; it self-skips cleanly on a bare IP with no known domain. Note: discovered vhosts land in `vhostfuzz_<port>.txt` for review — they are **not** auto-fed back into a second content-discovery wave (possible future work).

## AI evaluation layer (`evaluation/ai`)

Optional local-LLM findings triage over a finished scan's saved tool output. `striga.py` wires it: `_ai_llm_cfg()` (reads the `llm:` config section), `_ai_collect_findings()` (reads saved outputs into `RawFinding`s, skipping its own `ai_evaluation.*` report + binaries), `run_ai_evaluation()` (health-check → evaluate → render → save `ai_evaluation.{md,json,txt}`). Gated by `--ai-eval`/`--no-ai-eval` over `llm.enabled` (default on).

- **The AI import is lazy + guarded** — `from evaluation.ai import …` happens *inside* `run_ai_evaluation()`/`_ai_collect_findings()`, never at module top, wrapped in try/except. A missing/broken AI layer logs "AI evaluation layer unavailable; skipping" and core scanning/enum/exploitation keep working. **Keep it lazy** — a top-level import here previously took down the whole CLI (see next point).
- **`evaluation/ai/client.py` (`LLMClient`) is the backend client** the rest of the layer depends on (`__init__.build_evaluator`, `evaluator.py` both `from .client import LLMClient`). It was once missing entirely, which crashed every command on import. Contract: `LLMClient(provider, model, base_url, api_key, timeout, temperature, retries, options)`, `.health() -> bool`, `.complete_json(system, user, schema) -> dict`. Uses `requests` (no new dep). Supports **ollama** (`/api/chat`, structured-output `format=<schema>`, no auth header) and **openai-compatible** (`/v1/chat/completions`, `response_format=json_object`, Bearer key) — any provider that isn't `ollama` is treated as OpenAI-compatible. JSON is parsed leniently (code-fence/chatter tolerant); transient 5xx/network errors retry; a genuinely unparseable body raises so `evaluator.py` records a per-item notice.
- **Ollama needs no API key** — the `api_key`/Bearer path is only touched for openai-compatible providers. With `provider: ollama` and no `api_key_file`, everything works keyless. If Ollama is down, `health()` fails → clean skip; if Ollama is up but the model isn't pulled, each call errors → per-item notices (so `ollama pull <model>` before first use).
- **The model is a constrained classifier, not a reasoner.** Everything it emits is cross-checked deterministically in `evaluator.py` (evidence-verify against raw output, CVE grounding, CVSS-band severity). So instruction-following + strict JSON matter more than "security knowledge"; a strong general instruct model (default `qwen2.5:14b-instruct`) is a fine choice and a 7–8B model is a reasonable speed trade since the trust layer catches hallucinations.
- **CVSS grounding is fed from disk** (`_ai_target_cvss` in `striga.py`): harvests `{CVE: cvss}` from the vuln cache — nuclei `info.classification.cvss-score` (structural walk) + vulners/nmap-vuln `CVE  CVSS` lines (regex with a `(?!\d)` boundary so a CVE number isn't misread as a prefix of a longer one) — no network calls. Passed as `context["cvss"]` so `evaluator._ground_severity()` overrides the model's severity guess with the authoritative band. Only populated after a vuln-scan/exploitation pass has written the cache (so `--auto-all`/`--auto-exploit`, not `--auto-enum` alone). webtech-derived CVEs have no local CVSS (would need an NVD call — deliberately not done).

## Configuration

- `config.yaml` is the live framework config (scanner flags, enable/disable toggles, Metasploit RPC connection, LHOST/LPORT/CHOST/CPORT for callbacks, timeouts). `ConfigManager` (`core/config_manager.py`) is a singleton loaded once from `/opt/striga/config.yaml` by default; pass `--config` to override.
- `cve_mappings.json` — local CVE → exploit-module lookup table used before/alongside MITRE and Vulners API calls.
- `vulners_api.key` — expected to hold a Vulners API key; currently empty in this checkout.
- Config sections added this cycle: `performance` (`use_cache`, `max_concurrency`, `two_phase_scan`, `discovery_min_rate`, `hostname_scripts`), `web_enum` (`use_vhost`), `llm` (AI eval), plus scanner entries `feroxbuster`/`sslscan`/`wpscan`/`vhostfuzz`/`smbmap` and `web_tech_lookup.nvd_api_key_file`. **The deployed `/opt/striga/config.yaml` is what actually runs by default** (the banner may show an older version than the repo `config.yaml`) — new modules/keys only take effect after `install.sh` redeploys or with `--config ./config.yaml`. Optional untracked key files: `wpscan_api.key`, NVD key (path from `web_tech_lookup.nvd_api_key_file`).
- **Secrets in `config.yaml`**: `exploit_launcher.MSF_PASSWORD` is a live plaintext credential committed in-repo. Treat this as a leaked secret — flag it rather than propagate the pattern, and never add new secrets to tracked config files. Prefer environment variables or an untracked local override for credentials going forward.
- **`--config` staleness gotcha**: `ConfigManager` is a singleton that loads its *default* path (`/opt/striga/config.yaml`) the instant `core` is imported — which happens before `argparse` runs, i.e. before `--config` is ever known about. `--config` only takes effect later, inside `run_striga()`, via `config.reinitialize(args.config)`. Any config value read as a **module-level constant at import time** (e.g. `LHOST = config.get_config_value(...)` sitting bare at the top of a file) permanently captures whatever the *default* file said and silently ignores `--config` forever after — this bit `exploit_launcher.py` (LHOST/LPORT/MSF_PASSWORD/MSF_SERVER/MSF_PORT/CVE_DATABASE/etc, now reloaded via `_load_launcher_config()` called both at import and again from `init_launcher()`) and `poc_search.py`/`cve_finder.py` (now read inline inside their functions instead). **Always read config values live, inside the function that uses them (or a function explicitly re-called after `reinitialize()`), never as bare module-level constants** — this is the one pattern in this codebase that looks completely reasonable but is quietly broken under `--config`.

## Working conventions

- Match the existing per-service module shape when adding a new scanner or enumeration tool: a small wrapper module exposing a `run_<tool>_*` async function, registered through `core/scanner_adder.py` or `core/module_adder.py` / the `--add-scanner` / `--add-module` CLI flags, and enabled via `config.yaml`.
- Preserve the async/task-based fan-out in `enumeration()`/scanning in `striga.py` — enumeration tasks are dispatched conditionally on which services nmap found open. Use `bounded_gather()` (not bare `asyncio.gather`) for leaf subprocess task sets so the global concurrency cap applies; keep orchestrator gathers (`--auto-all` across targets) unbounded to avoid semaphore deadlock.
- New web modules take `(target, port, scheme, host=None)` and route the vhost via Host header / SNI (non-persistent — never write `/etc/hosts`). New tools that reuse an existing binary under a distinct config key (like `vhostfuzz`→ffuf, `nmap-http`→nmap) hardcode the binary in the module and keep the module name only for `enabled`/`get_tool_flags`/result files/`services.json`.
- Read config values live inside functions (never as import-time module constants — see the `--config` staleness gotcha). Optional/external layers (AI eval, backend clients) must import lazily and degrade gracefully, never break core scanning on import.
- Keep `run_script`'s filename validation and the interpreter allowlist (`.py/.sh/.js/.pl/.rb/.ps1/.php`) intact when touching script dispatch; this is the framework's guard against arbitrary code execution via crafted script names.
